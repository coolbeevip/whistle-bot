# ESP32-S3 小车下位机程序架构设计

## 目标与实物基线

电脑、树莓派和手机均可作为上位机。车上有线连接用 USB 串口，桌面遥控和手机浏览器用 Wi-Fi。两种连接使用同一套命令、单位、控制权和停车规则。ESP32-S3 在车上执行运动指令，采集编码器和传感器数据；路径规划、地图和可视化由上位机承担。

参考底盘使用 M3 左轮与 M4 右轮。USB 串口桥为 CP2102N，驱动板固件基线为 1.7.3。本文同时记录已实现模块、扩展设计与需要在目标车上验证的指标。接线和板卡版本见[硬件配置](hardware.md)，独立诊断程序见 [UART 检查](../firmware/uart_check/)。

## 通信路径与程序分工

```text
电脑 / 树莓派 ── USB 串口 ──────┐
手机 / 电脑 ─── Wi-Fi WebSocket ─┴─ 协议解析 ── 控制权与运动状态 ── 电机驱动 ── UART1 ── 亚博板
                                      ↑                                 │
                                      └── 状态与遥测 ← 编码器、故障、扩展传感器 ─┘
```

| 固件组成 | 负责的工作 |
| --- | --- |
| USB 与 WebSocket 接口 | 收发完整消息，为每条消息标记连接身份。各自维护有限缓冲，向同一个命令处理入口提交请求。 |
| 板载 Web 面板 | ESP32 的 HTTP 服务提供随固件发布的静态页面，浏览器通过同源 WebSocket 调用上位机协议。手机与 USB 上位机共用运动控制和停车逻辑。 |
| 协议处理 | 校验版本、长度、字段、单位和请求编号，生成统一应答。新增上位机客户端可以直接复用协议示例。 |
| 运动控制 | 独占管理控制权、目标速度、速度上限、失联计时和停车。只有该模块可要求电机驱动改变输出。 |
| 亚博板驱动 | 独占 UART1，封装速度、零输出、编码器上报和反馈解析。将逻辑左右轮映射到物理通道和正反方向。 |
| 设备配置与遥测 | 集中保存引脚、总线、轮子映射、设备能力及采样周期。每个样本携带启动后的单调时间戳和有效状态。 |

## 软件项目架构

正式固件位于 `firmware/controller/`，沿用 PlatformIO、Arduino-ESP32 和已验证的八线 Flash 配置。`firmware/uart_check/` 保留为独立的接线诊断工程。首版实现位于 [controller](../firmware/controller)，下列目录说明模块职责。

```text
firmware/controller/
  platformio.ini
  src/
    main.cpp           装配板级配置、驱动、任务和消息通道
    board/             本车引脚、总线分配、设备能力与配置校验
    control/           驾驶权、停车状态机、差速动作、标定计算
    protocol/          v1 请求校验、应答编码、动作去重和会话管理
    transport/         USB 帧收发、HTTP 静态资源、WebSocket 连接
    drivers/           亚博 UART1 收发；按需加入雷达、IMU 驱动
    runtime/           FreeRTOS 任务、单调时钟、跨任务消息和时序统计
    sensors/           可选雷达数据源与扇区有效性判断
    storage/           版本化标定参数的读取、校验和提交
  web/                 手机页面源码，构建时打包到固件 Flash
  test/                宿主机运动算法与驱动串口帧测试
```

依赖方向为 `transport → protocol → 类型化请求 → control`。控制逻辑接收带时间戳的请求与反馈，输出轮速目标、停车决定和状态快照。它可以用普通 C++ 和模拟时钟独立测试，无需 Arduino、USB、JSON、网页或真实电机。由 `runtime` 把决定交给 `drivers`；只有亚博驱动可写 UART1。标定计算属于 `control`，非易失写入由 `storage` 执行。新增激光雷达只需提供带坐标约定、时间戳和有效期的观测，并注册设备能力；涉及运动限制时，由控制任务消费该观测并作决定。

### 实时任务与数据所有权

以下为首版调度预算。控制任务绑定一个应用 CPU 核，应用层网络和雷达解析任务安排到另一核或以较低优先级运行。实现时检查实际框架任务、UART 中断和系统任务的核分配，并在目标板测量。各模块可以共用任务，目录数量不决定任务数量。

| 执行单元 | 唤醒与职责 | 时间和资源约束 |
| --- | --- | --- |
| 运动控制任务，应用最高优先级 | 单独持有驾驶权、动作状态和 UART1 输出。按绝对时间每 10 ms 执行一次运动更新；显式停车、故障或驾驶权截止定时器可提前唤醒同一任务。 | 每次先处理停车和超时，再读反馈快照、更新动作并发出至多一个电机目标。初始预算为周期唤醒延迟 ≤1 ms、单次计算 ≤2 ms。提前唤醒不移动下个周期的计划时间。 |
| 电机反馈接收，高优先级 | UART 接收缓冲到数后分段解析；完整合法帧生成包含两轮计数、序号和接收时刻的快照。 | 固定大小缓冲，每轮限定解析字节数。溢出或缺帧标记反馈无效，控制任务自行判断是否停车。 |
| 上位机通信，普通优先级 | 收完整帧、解析 JSON、校验会话，提交类型化请求并返回结果。USB 与 Wi-Fi 共用一份控制状态快照。 | 每连接限制输入、输出及每轮处理帧数。慢客户端丢弃旧遥测；控制应答仍无法送达时断开该连接。 |
| 扩展采集和后台作业，较低优先级 | 传感器分批解码，面板分块发送资源，后台处理诊断及标定提交。 | 雷达使用有界缓冲，满时记丢帧。Flash 写入只允许在确认停稳、禁止领取驾驶权期间进行，写完并校验后才解除限制。 |

控制循环启动前分配队列和缓冲。循环内只使用定长消息、短临界区快照和有界非阻塞操作；禁止等待网络、串口腾空、文件写入或互斥锁持有者，也不做 JSON 解析、动态内存分配及同步日志。串口反馈的过期判断使用接收时刻，不能因重新读取同一快照而续期。

### 停车通道、背压与截止时间

- **跨任务消息。** 手动目标使用单槽覆盖邮箱，携带会话、驾驶令牌、请求编号和到期时间；提交一次的动作及标定操作使用固定深度队列，满时返回 `BUSY`。停车、断连和故障走独立锁存标志及任务通知，即使普通队列满也能唤醒控制任务。控制任务先撤销令牌，再清理旧请求。只发布完整状态快照给通信任务，避免上位机读到一半更新的左右轮数据。
- **旧包与续期。** 进入网络缓冲的旧指令也可能按序迟到。首版 v1 的运动会话应增加设备签发的短时有效凭据：设备在授权应答中提供首个窗口，并每 100 ms 向持有者发布新的 `control_window` 事件（字段为 `window`、`expires_at_ms`）；每个窗口从签发起有效 300 ms，绑定本轮令牌，客户端随 `drive`、动作启动、标定点动及 `heartbeat` 回传。控制任务检查窗口与当前令牌，续期上限取“最近有效刷新被受理后 300 ms”和该窗口截止时间的较早者。重复或过期消息不续期。浏览器锁屏期间积压的数据因此不能持续延长授权。
- **UART1 输出。** 驱动以非阻塞方式提交完整帧，限制待发送的普通目标，禁止在底层 TX 环形缓冲中堆积多帧车速。停车时丢弃所有尚未开始发送的旧目标；已经开始的帧发完后，零 PWM 帧紧随其后。按 115200、8N1 计，每字节占 10 位时间；若在途普通帧限为 32 字节，随后 13 字节以内的零输出帧合计约 3.91 ms。实现须核实实际帧长及缓冲行为；串口故障立即上报停车发送失败。
- **时间口径。** 驾驶权截止定时器独立于 10 ms 运动更新，回调只唤醒控制任务。以设备最后受理的有效刷新为起点，要求 310 ms 内在 UART1 TX 引脚观察到完整零输出帧。300 ms 授权期之外的 10 ms 预算包含唤醒、调度、处理和在途串行发送。车轮停稳另按编码器测量。若一个控制周期未完成即进入下一周期，置时序故障、取消动作并优先请求停车；不补发漏掉的非零目标。主控卡死或掉电时的停车能力由板间断链试验另行验证。

## 上位机怎样连接

| 项目 | USB | Wi-Fi |
| --- | --- | --- |
| 物理入口 | 数据线插 ESP32 标有 `UART` 的 USB 口，经 CP2102N 连接 `Serial`，115200、8N1。上位机按设备枚举选择端口。 | 首版让 ESP32 建立带独立密码的热点，网关固定为 `192.168.4.1`。网页从同一地址加载。 |
| 应用入口 | UTF-8，每个 JSON 对象一行，以 LF 结束，兼容 CRLF。客户端打开端口可能触发复位，应等待启动并重新握手。 | `ws://192.168.4.1/ws`，每个 WebSocket 文本消息一个 JSON 对象。网页和树莓派客户端使用相同路径。 |
| 连接管理 | 单个主机进程持有串口。握手前可丢弃 ROM 启动文本，正常运行期的诊断输出封装为事件。 | 每条连接有独立会话。首版仅向本地热点开放控制服务，浏览器请求校验 Origin；接入共享网络时再增加应用认证和加密传输。 |

板间 UART1 固定使用本车配置的 TX GPIO17、RX GPIO18，波特率 115200、8N1。ESP32 将左右轮命令翻译成亚博格式；驱动板 USB Type-C 用于独立检修。两路上位机接口可以同时查询状态，同一时刻仅允许一个会话驾驶。

## 板载 Web 控制面板（首版）

手机连接小车热点后，在浏览器打开 `http://192.168.4.1/`。HTML、CSS 和 JavaScript 存放在 ESP32 的 Flash 中，手机离线即可加载。页面打开同源 `/ws`，先执行 `hello` 和 `status`，再订阅 `encoders`。打开页面、刷新和断线重连都从只读状态开始。

### 手机页面布局

| 位置 | 内容与操作 |
| --- | --- |
| 顶部状态区 | 分别显示手机到 ESP32 的连接状态、亚博驱动板是否就绪，以及驾驶权归属（空闲、本页面、其他 Wi-Fi 会话或 USB 上位机）。断线时标记数据过期，并保留最后更新时间。 |
| 中部驾驶区 | 竖屏排列前进、后退、左转、右转四个按住式按钮，中间设独立的“停车”键。握手成功即可使用停车键，包括其他会话正在驾驶时。方向键在驱动板就绪、底盘已标定后可用。 |
| 速度与反馈区 | 默认使用已标定的低速档。速度选择范围受设备公布的 `max_abs_mm_s` 限制。左右轮分别显示目标速度、编码器累计计数和反馈有效性；收到停车应答后显示“已发停车”，反馈确认后才显示“已停稳”。 |

### 从观察到驾驶

1. **按下方向键。** 驾驶权空闲时，按下即表示用户申请该方向的手动驾驶。页面发送 `claim`，只有收到授权且原触点仍按住时才发送第一条 `drive`，之后按 10 Hz 刷新。若授权返回前已经松手，直接释放本次授权（`stop`）。重复触点不叠加。设所选速度为正数 `s`，按（左轮，右轮）依次约定前进 `(+s,+s)`、后退 `(-s,-s)`、原地左转 `(-s,+s)`、原地右转 `(+s,-s)`。
2. **松手或页面中断。** 本页面正在驾驶时，松手、触摸取消、窗口失焦或切到后台立即清除按住状态、停止刷新并尝试发送 `stop`。若锁屏或断网导致消息未送达，固件按 300 ms 超时停车。重新连上后必须重新按方向键，页面丢弃旧触点和旧驾驶令牌。只读页面退出不影响正在驾驶的会话。
3. **从树莓派接管。** 当 USB 上位机持有驾驶权时，页面保持方向键禁用，允许观察和点击“停车”。由操作者先停车，待反馈确认停稳、驾驶权空闲后，再按方向键申请手动驾驶。若并发申请返回 `BUSY`，显示最新归属并等待下一次手动操作。
4. **故障与扩展。** 驱动板掉线或反馈过期时，页面显示故障、禁止新的运动请求，停车键在与 ESP32 的连接有效时保持可用。以后按 `hello` 返回的能力增加测距或 IMU 状态，地图与完整扫描画面由上位机呈现。

### 底盘标定向导

面板分为驾驶、定距与定角、标定三个页面，共用停车按钮。“标定”总览从设备读取保存版本以及各项状态。点选一项开始独占会话，编辑和复测都留在本项页面。所有写入通过存储任务完成，成功回报后才更新已保存状态。

| 项目 | 采样与复测 | 保存后的影响 |
| --- | --- | --- |
| 轮子与方向 | 架空点动通道，核对左右侧、电机和编码器极性。 | 首次保存后可标定距离。改变映射将清除依赖它的标定值。 |
| 距离 | 输入两轮的共同实际行程，计算各自的毫米/计数。可以在取得完整轮距参数前进行直线复测。 | 允许先保存样本结果，再返回复测。重新计算后保留已有轮距，距离和转角都需重新复测。 |
| 转角 | 使用已保存的距离系数，从地面实测转角反算有效轮距，在同页设置复测角度。 | 保留距离系数与直线复测状态。 |

每次保存都将当前阶段与依赖状态一起原子写入同一份 NVS 记录。`cal_checkpoint` 允许提交完整方向、有效距离或转角的中间进度；原有 `cal_commit` 仍要求两项复测均已通过。旧固件保存的完整有效标定视为已经复测。控制权、窗口、反馈、停车与运动互锁同样适用于阶段保存。基础手动遥控可用本车默认方向，drive_low 的 left_dir 和 right_dir 分别取 −1、0 或 1，省略 ticks_s 时输出限幅 PWM 400，可选整数 ticks_s 的范围为 150–9000。定速和定距需要已保存并复测的距离系数，定角还需要已保存并复测的轮距。

点动松手即停，单次点动在固件端设置时长上限。采样和试跑期间页面保持心跳，失联、点击全局“停车”或另一会话要求停车时，中止本次标定运动并释放控制权。未保存的修改可以放弃；更换轮胎、调整轮距或更换电机后可重新进入向导。里程与角度均为轮式里程计估计，打滑时需依靠外部实测发现偏差。

### 定距和定角动作

完成标定后，驾驶页开放“按距离行驶”和“按角度原地转向”。操作者选择方向并输入米数或度数，例如“后退 0.5 m”“左转 90°”。点击执行后页面显示目标、编码器估计进度和停止原因，保留随时可用的停车键。ESP32 在动作开始时记录计数基线，按左右轮行程均值计算直行距离，按行程差除以有效轮距计算车体转角。接近目标时减速，进入目标容差且反馈确认停稳后发布完成事件。单次动作设超时；持续无进展或反馈失效时终止并报告故障。

**动作控制。** 建议在 ESP32 上生成左右轮目标行程。直行距离为 `d` 时，两轮目标均为 `d`；左转角为 `θ`（弧度）、有效轮距为 `B` 时，目标分别为 `−Bθ/2` 和 `+Bθ/2`。每次用同一帧两轮计数和同一版标定系数更新各轮误差，向亚博板发送限速、限加速度的轮速目标。某一轮持续停滞或方向错误时，两轮一起停车；另一轮的进度不能抵消该故障。计数器回绕按计数位宽计算有符号增量，驱动板重启或增量超过本周期物理上限时，使当前基线失效并取消动作。

**完成判据。** 发出零输出后，必须有连续的新鲜编码器帧覆盖停稳观察窗，且两轮计数变化均在静止噪声阈值内。只有两轮各自的最终行程误差都在容差内才报告 `completed`；滑行越界则报告 `failed` 并附最终误差。轮速上限、动作范围、距离与角度容差、静止阈值、观察窗和无进展时限随底盘配置记录，面板显示生效值。试车时用独立量具另测整车误差，编码器判定完成与实车精度分别验收。

## v1 消息协议

每个请求含 `v`、`id`、`op`。协议版本取整数 `1`，`id` 为会话内递增正整数。请求帧最多 1024 字节。USB 收包支持分段和一次到达多行；超长行丢弃至下一个 LF。Wi-Fi 超长消息整条拒绝。格式错误、未知版本、未知命令及越界值均返回错误，保持原运动截止时间。

| 命令 | 输入与结果 |
| --- | --- |
| `hello` | 建立逻辑会话，返回 `boot_id`、`session`、协议版本、已启用设备能力和左右轮限速。重复握手使该连接的旧会话失效；若旧会话在驾驶，先停车。 |
| `claim` | 携带 `session` 请求驾驶权。仅在电机链路就绪、底盘已标定、驾驶权空闲且已确认停稳时授予，返回本轮 `lease`。竞争失败返回 `BUSY`。 |
| `drive` | 携带 `session`、`lease`、有符号整数 `left_mm_s` 和 `right_mm_s`。正值表示车体前进方向。超限整条拒绝，允许范围由 `hello` 公布。 |
| `move_distance` / `turn_angle` | 持有驾驶权后一次提交 `distance_mm`（正前负后）或 `angle_deg`（正左负右），返回 `action_id`。同时只执行一个动作；运行中拒绝新的运动目标。状态查询和进度、完成或取消事件均带该标识。 |
| `heartbeat` | 在定距、定角或标定会话中，持有者以 10 Hz 携带 `session`、`lease` 和新请求编号续期。超时沿用 300 ms 停车规则；重连后需由操作者重新发起动作。 |
| `cal_begin` / `cal_sample` / `cal_commit` / `cal_cancel` | 申请专用标定权、逐步采集或复测、保存、放弃。沿用同一会话和独占令牌；`cal_begin` 可在未标定时使用，保存或放弃后释放令牌。USB 与网页共用这组操作。 |
| `stop` | 任一已握手会话都可要求四路输出归零，同时撤销当前驾驶权。重复执行仍然停车。 |
| `status` | 返回启动标识、运动状态、驱动板就绪状态、驾驶权归属（相对当前会话）、左右轮目标、停稳与反馈有效状态、左右编码器累计计数和最近故障。驾驶权归属变化和故障变化时向已握手会话推送状态更新；响应与广播均不披露其他会话的驾驶令牌。 |
| `subscribe` | 连接指定遥测主题，例如 `encoders`，首版支持 1–10 Hz。断开后清理订阅。设备能力表列出实际支持的主题。 |

下面是一次会话中的示例报文，每行独立；USB 使用行分隔，WebSocket 逐条发送。示例中的会话、驾驶权和限速由设备在运行时产生。

```jsonl
{"v":1,"id":1,"op":"hello"}
{"v":1,"id":1,"ok":true,"boot_id":7,"session":14,"capabilities":["drive","encoders"],"max_abs_mm_s":100}
{"v":1,"id":2,"op":"claim","session":14}
{"v":1,"id":2,"ok":true,"lease":93,"window":104}
{"v":1,"id":3,"op":"drive","session":14,"lease":93,"window":104,"left_mm_s":50,"right_mm_s":50}
{"v":1,"id":3,"ok":true}
{"v":1,"event":"encoders","t_ms":4980,"left_ticks":104,"right_ticks":134,"valid":true}
{"v":1,"id":4,"op":"stop","session":14}
{"v":1,"id":4,"ok":true}
```

遥测示例假定客户端已订阅。应答的 `id` 对应原请求；错误示例为 `{"v":1,"id":3,"ok":false,"error":"NOT_OWNER"}`。成功的动作提交应答表示固件已受理目标；`stop` 成功应答表示已向 UART1 提交零输出，串口发送失败则返回故障。实际转动由后续编码器反馈确认。同一会话重发最后一条相同请求时返回缓存结果，不重复驱动或延长时限。更早的编号、同编号不同内容或已失效的驾驶令牌均拒绝；新连接和复位后必须重新握手。

**动作重试与查询。** 定距和定角请求另带由客户端生成的 `request_key`，在本次启动内唯一。固件在活动期间及终态后保留最近的动作记录（建议 16 条），先校验会话与权限，再按键去重。同键同目标返回原 `action_id` 和状态，同键不同目标返回 `CONFLICT`。同一会话的迟到旧请求只能查询已有结果；禁止重新启动。应答丢失后，客户端可用只读 `status` 携带 `request_key` 查询目标、进度、终态和停止原因。记录已淘汰或 `boot_id` 改变时报告结果未知，由操作者决定是否发起新动作。重连只恢复观察。

**标定请求的边界。** `cal_sample` 需指定步骤和操作：`jog` 指定物理通道及方向，由设备限制输出与时长；`jog_stop` 结束点动并保留向导；`map` 记录左右与符号；`start`、`finish` 配对记录样本，实测值按步骤使用 mm 或度；`trial` 用候选值在标定限速下复测。本轮点动到期自动归零，心跳仅保持会话。提交时验证步骤完整、当前标定版本与进入时一致且已停稳。非易失存储写入或校验失败时保留原版本并返回错误。

## 驾驶权、停车与故障

1. **上电和复位。** 先向亚博板发送四路零 PWM，再查询板卡和编码器。只有通道映射、方向及速度参数已验证时才开放 `drive`，未标定时仍可查询。每次启动生成新的 `boot_id`。
2. **行驶。** 授权后设置最长 300 ms 截止时间，具体取值受设备签发窗口限制。手动驾驶以 10 Hz 发送新的 `drive` 续期；定距、定角仅提交一次目标，由持有者以 10 Hz 发送 `heartbeat` 续期。标定流程也用心跳续期。手动驾驶中的心跳不能维持上一条非零速度。状态查询、遥测和其他连接的流量均不续期。持有驾驶权的网页松手、失焦或进入后台时主动发 `stop`。
3. **失联与切换。** 控制循环以 10 ms 为目标周期检查截止时间。到期、驾驶会话明确断开或收到停车请求时，清空待发速度，优先发送 `$pwm:0,0,0,0#`，撤销驾驶权。USB 断开不一定能立即检测，由超时兜底。换接口后重新 `claim`，旧会话积压的速度指令不得恢复运动。
4. **板间链路异常。** 行驶中应持续收到编码器上报；反馈中断超过 300 ms 或驱动板复位，进入故障态并尝试发送零输出。恢复链路后先发零输出并重新探测，再接受新的驾驶请求。上位机状态中要区分“已要求停车”和“反馈确认停稳”。

停车、超时和故障在同一个运动控制循环内撤销令牌、清除旧目标并进入 `stopping`。发送每条非零输出前再次核对令牌与截止时间。期间所有会话仍可停车或查询；新驾驶与标定申请须等反馈确认停稳。缺少反馈时保持故障，面板显示“停稳未知”。动作取消、失败和完成各产生一次终态事件，终态后释放令牌；客户端须重新申请才能开始下一次驾驶。

300 ms 是上位机失联后下位机触发停车的设计时限；车轮还有机械滑行时间。若 ESP32 随 USB 拔出而掉电，或板间 TX 线断开，软件可能无法送达停车命令。独立供电上车前，应架空测试亚博板在这些情况下是否保持旧输出；若会保持，应增加独立电机使能或断电手段。该故障不能靠 Wi-Fi 心跳解决。

## 执行周期与硬件扩容

运动控制和 UART1 接收采用非阻塞处理。每周期先处理停车、超时和电机反馈，再处理普通请求。每个驾驶会话只保留最新的待发速度；网络发送慢时丢弃旧遥测并累计丢包数。编码器原始计数可先于速度标定使用。亚博板当前保存的轮径、编码器线数和减速比需与实物核对后，才能承诺 mm/s 和里程精度。

每增加一种设备，先在板级配置中登记总线、引脚、电平、供电电流、采样频率和超时，再实现初始化、周期读取和故障上报。启动时检查引脚、UART、I²C 地址冲突；`hello` 公布已启用能力，`status` 区分在线、失联和数据过期。选配器件掉线时，只禁用依赖它的功能；若它被设为行驶必需的避障传感器，则进入停车流程。

| 扩展例子 | 接入决策 |
| --- | --- |
| IMU、低速测距模块 | 可共用单独规划的 I²C 总线，核对地址和上拉电压。读数加时间戳；单次读取设置超时。 |
| TTL 串口激光雷达 | 选型后分配空闲硬件 UART 和 GPIO，保留电机 UART1 与上位机调试串口。核对电平、启动电流及原始数据率，再决定上传距离摘要或扫描帧。 |
| USB 雷达或用于 SLAM 的高带宽雷达 | 优先直接连接树莓派或电脑，由上位机处理扫描、定位与规划。下位机继续接收轮速并回传编码器。 |

USB 上位机链路在 115200、8N1 下，每方向理论上限约 11.5 kB/s，实际有效吞吐还要扣除协议开销。添加传感器前按“每帧字节数 × 频率”核算预算，为指令和停车应答留余量；不把原始高频扫描默认塞进电机遥测队列。

### 激光雷达接入方案

首版允许在未安装雷达时完成底盘标定、遥控和定距动作。若希望小车在没有树莓派时也能按障碍距离停车，优先评估将带距离输出的雷达接到 ESP32。若目标是二维建图、定位或导航，优先将扫描雷达接到树莓派。两种方案沿用现有轮速、编码器和停车协议。

| 部署位置 | 数据流与职责 |
| --- | --- |
| ESP32 直连 | 雷达驱动完成收包、校验和单位转换，按车体方向生成有效距离摘要。运动控制每周期读取最新摘要；即使手机没有订阅遥测，本地避障仍可工作。根据设备视场仅发布实际覆盖的方向。 |
| 树莓派直连 | 树莓派读取完整扫描并结合轮式里程计做定位、规划和避障。ESP32 上报两轮计数、采样时间、启动标识及标定版本，供上位机把轮子运动与扫描对齐。上位机对两个设备的时钟建立映射，记录雷达相对车轴中心的安装位姿。ESP32 面板只展示本机可验证的数据。 |

**硬件预留。** 保留 UART1 给亚博板，保留接入 CP2102N 的串口给上位机。在板级配置中为可选雷达留出独立总线配置项；车型与雷达型号确定后，再按实物开发板和模组的引脚占用选择引脚。选型记录需包含接口类型与电平、供电及启动峰值电流、视场与盲区、扫描周期和最大数据率。底座为雷达保留无遮挡的安装位置、稳压供电余量和走线空间。

**数据接口。** ESP32 配置本地雷达后，`hello` 公布 `lidar_sectors` 能力，现有 `subscribe` 可订阅同名主题。面板显示扇区最近有效距离、样本年龄和设备状态。车体正前为 0°，逆时针为正；扇区角度由安装位姿转换后给出。距离单位为毫米，时间戳取 ESP32 单调时钟的采样时刻。下例表示前方扇区取得一个有效样本：

```json
{"v":1,"event":"lidar_sectors","seq":38,"t_ms":12400,"sectors":[{"from_deg":-15,"to_deg":15,"min_mm":625,"valid":true}]}
```

无有效回波或扇区覆盖不足时返回 `valid:false`、`min_mm:null`。驱动在有界缓冲内增量解析，超长或损坏的帧丢弃并重新同步；旧帧、无效帧和重复帧均不能刷新数据有效期。网络遥测队列拥塞时只保留最新摘要，停车判断直接读取本地样本。

**运行策略。** 观察模式仅展示距离。启用本地避障后，固件按当前动作检查路径所需扇区，前进、倒车及原地转向分别考虑各自的车体扫过范围。未覆盖或过期时拒绝依赖该覆盖的动作；行驶中遇障、失去覆盖或雷达掉线时取消动作并停车。障碍消失后须重新取得控制权。触发距离根据外壳相对传感器的位置、该速度下的制动距离、采样与处理延迟和余量在实车上确定。树莓派承担避障时，应在扫描过期时主动发 `stop`、撤销未完成动作并停止运动续期，以覆盖“上位机仍在线但雷达已经掉线”的情况。

## 实施顺序与实车验收

测试记录附带固件版本、标定版本、供电方式、地面材质及生效阈值。区分 ESP32 独立供电时拔掉 USB 数据链路，与拔线导致 ESP32 同时掉电两种工况。前者测软件超时，后者单独观察驱动板实际输出。处于 Wi-Fi 独立运行工况时，先明确 ESP32 的稳压供电接法；当前 USB 供电的接线仅验证了桌面工况。

| 阶段 | 可观察的通过条件 |
| --- | --- |
| 1. USB 协议与底盘映射 | 保持车轮悬空，USB 客户端完成握手和状态查询；分别点动 M3、M4，记录左右侧、正向及编码器符号。复位后输出为零。 |
| 2. 单接口运动 | 限速标定后，两轮分别执行带单位的速度请求。停止刷新后，在最后一条有效命令起 310 ms 内观察到下位机发出零 PWM，以编码器另行记录停稳时间。 |
| 3. Wi-Fi 与 USB 并存 | 用同一组协议用例分别通过串口和 WebSocket 执行。两端同时申请时仅一端获权；另一端可观察并停车。模拟网页关闭、USB 中断、重连和旧包重发，验证不会自行起步。 |
| 3a. 手机面板实测 | ESP32 独立供电、电脑 USB 拔除后，手机离线连热点打开首页，低速验证四个方向、松手停车和左右轮计数。分别测试快速点按（授权回复前松手）、锁屏、刷新及断网重连，确认不会意外起步。再接入 USB 上位机驾驶，核对页面显示归属、主动停车和手动接管。 |
| 3b. 手机标定与动作复测 | 从无标定状态走完向导，确认取消保留旧值、保存后重启可读回同一版本。分别通过 USB 和网页提交带符号的距离、角度指令，使用卷尺和地面方向线记录实际误差；执行中停车或断网应取消动作，重连后保持静止。 |
| 3c. 边界与竞态 | 让动作提交应答丢失并继续发送心跳，通过查询确认同一动作只启动一次。停车与旧速度同时到达、两端争抢以及轮子滑行期间尝试接管，均不得产生迟到的非零输出。架空模拟单侧编码器无进展、反馈消失或驱动板复位，核对故障、最终误差和停稳状态。 |
| 4. 故障及扩展负载 | 分别断开板间反馈、切断主控供电并记录电机实际表现；对超长帧、慢客户端和传感器数据突发进行测试，核对停车截止时间、故障状态及遥测丢包数。 |
| 4a. 实时性台架验收 | 对照空载与 Web 页面加载、USB/Wi-Fi 并发、雷达峰值输入、慢订阅者同时存在的工况。分别记录周期唤醒延迟、执行耗时、截止违约次数、队列最高水位和遥测丢帧；报告观测最大值及测试时长。用调试 GPIO 标记有效刷新受理时刻，用逻辑分析仪捕获 UART1 最后一个停车字节。覆盖普通 TX 刚开始、请求队列已满、旧包延迟到达等边界，逐项核对实时预算。超预算时先限制后台工作量再复测，通过前保持台架验证状态。 |
| 5. 雷达接入回归 | 无雷达配置下复测 USB 和 Wi-Fi 驾驶。直连方案先用录制帧验证左右方向、量距单位、盲区和过期判定，再以峰值数据率复测原有 310 ms 失联停车指标。低速实车测量不同速度下的障碍停车距离。树莓派方案单独拔掉雷达并保持上位机连接，确认动作取消，重插后小车保持静止。 |

实现时可直接复用现有工程中的 UART1 初始化和已验证的查询报文；先跑通 USB 协议，再让 WebSocket 接入同一命令处理入口。[Arduino-ESP32 串口接口](https://docs.espressif.com/projects/arduino-esp32/en/latest/api/serial.html) · [Arduino-ESP32 Wi-Fi 接口](https://docs.espressif.com/projects/arduino-esp32/en/latest/api/wifi.html)

## 双轮控制与落地验证

ESP32 以 10 ms 周期调速，按驱动板编码器帧的本地接收时间累积至少 40 ms 后估算速率。反馈中断超过有效期时重新建立测速基线。网页以 m/s 设速度，默认 0.40。未验证距离时根据 67.5 mm 轮径与实测 1783 ticks/rev 换算为 drive_low 的 ticks_s；旧客户端省略速度时仍请求 200 ticks/s，控制器假设左右轮每圈计数相近。验证距离后按每轮独立的 mm/tick 调速。控制器将速度归一化，使用速度前馈、渐入的摩擦补偿、带输出饱和保护的 PI 和目标速度斜坡。手机手动驾驶使用亚博板 ±3600 的 PWM 指令范围。距离验证后滑块仍显示 m/s，发送 drive 的 mm/s 参数，上限取 1060 mm/s 与两轮 9000 ticks/s 换算结果中的最小值。定距和定角动作仍限幅 650。系数和目标速度为调试初值。控制器在连续直行中记录起点，按左右轮行程差小幅降低领先轮的目标速度。原始计数差 4 ticks 以内（已标定时为 1 mm）不增加修正，修正上限为目标速度的 10%，并限制修正变化速率。drive 和 drive_low 支持 acceleration 参数（smooth 或 responsive）。省略时使用原有 smooth 斜坡，responsive 将手动轮速斜坡与高速直行目标上升速率提高到三倍。板载 CSV 的 responsive 列记录该模式。停止或转向会结束该次直行。

定距和定角按共同的剩余行程生成速度，再依据左右轮进度差调整两轮目标。单轮进入容差带后目标归零。结果检查仍按两轮分别判定，车辆停稳后报告动作结果。命令失效、反馈丢失、堵转和显式停车继续直接输出零 PWM。

上位机也可在完整标定后发送 `drive_twist`，附上与 `drive` 相同的控制权和窗口。整数参数 `linear_mm_s` 范围为 −100 到 100，`angular_mrad_s` 范围为 −4000 到 4000，正方向分别为前进与逆时针。超过轮速上限时，两轮速度按同一比例缩放。完整标定且反馈有效时，状态帧中的 `wheel_odom` 给出驱动板反馈的 ESP32 接收时间、轴心 x/y 毫米和相对航向弧度，前进为 x 正向、左侧为 y 正向。启动、编码器复位或标定修订后重新建立原点。该估计只使用车轮反馈。

手机的 Vehicle telemetry 可导出页面接收到的最近一次驾驶记录，最多 3000 个样本，订阅频率 5 Hz。CSV 中 `t_ms` 表示事件时刻，`rate_at_ms`、`rate_window_ms` 分别表示测速窗口终点与跨度。左右目标为斜坡后的 ticks/s，实测为带前进正号的 ticks/s；PWM 是串口最后发送的值，符号保留实际电机接线方向。分析时按时间戳对齐，同一反馈窗口可能出现在多次状态查询中。

落地验收时，在同一地面沿 1 m 标线前进、倒退各三次，记录起步 20 cm 处和终点的横向偏差、终点朝向及 CSV。万向轮可分别顺直和横置起步。若 PWM 持续达到上限而一侧速度偏低，先核对两轮每圈计数和机械阻力。距离验证后，在外部角度标记上各做三次左右 90°，分别记录实际角度和停稳误差。连续动作再用顺时针及逆时针方形路线检查终点偏移。以外部测量值评估地面表现。

### 板载驾驶记录

ESP32 开始行驶时自动在内存中以约 10 Hz 记录，控制权释放或故障停车时交给后台写入 LittleFS。每次保留末尾 400 个采样点，文件头含实际采样总数和结束原因。最近 24 个已完成的 CSV 按运行序号轮换，写入临时文件并重命名成功后才轮换旧记录。掉电前尚在 RAM 中的一趟可能丢失。请求速度、斜坡目标、实际轮速单位均为 ticks/s；PWM 带实际电机接线符号。电池电压单位 mV，0 表示该样本未取得有效电压。

USB 和 Wi-Fi 均可用只读命令 `drive_log` 查询最新序号与写入状态，带 `run`、`offset` 可分段取回同一份 CSV。在电脑端用 `tools/read_drive_log.py` 通过 USB 自动取回文件并统计最高直行档位的稳态轮速与输出饱和比例。驾驶者无需打开遥测面板。

手动直行或后退时（已标定模式按每轮距离系数换算至等效计数速率），超过 1750 ticks/s 的设定作为速度上限。共同目标从 1750 起步，当两轮有输出余量并跟上目标时逐渐上探；当输出持续接近限幅且较慢轮落后时，两轮共同降速。行程差修正在共同目标上叠加。板载日志的 cruise_limit_ticks_s 记录这一上限，0 表示该功能未介入。

### 手机手动驾驶的控制权交接

方向键按下、松开与下一次按下使用独立序号。旧请求迟到的回复只处理对应的那次操作。停车收尾期间，手指仍按着新方向时，页面可在 800 ms 内重试申请；松手、切到后台或检测到其他控制端时结束等待。设备返回的 BUSY 同时附带 owner，用于区别停车收尾和其他控制端占用。

手动驾驶优先在收到与本次 lease 相符的 control_window 后续发；同一次按压最多有一条驾驶命令在途。若设备返回 STALE_WINDOW，且确认当前会话仍拥有同一个 lease，回复包含当前窗口，页面可在仍按住时重试一次。控制权过期或丢失后须重新按下。窗口刷新失败不会延长设备端的驾驶期限。
