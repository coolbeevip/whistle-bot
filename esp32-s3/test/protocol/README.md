# v1 协议基线

从仓库根目录执行以下命令，需要 Node.js 22、C++17 编译器和项目的 ArduinoJson 头文件。已有 PlatformIO 项目依赖时可以直接运行脚本；也可以通过环境变量 `ARDUINOJSON_SRC` 指定 ArduinoJson 的 `src` 目录。

```sh
pio pkg install -d esp32-s3
sh esp32-s3/test/protocol/run.sh firmware
sh esp32-s3/test/protocol/run.sh android
```

省略参数会依次运行两端。退出码 0 表示该次选择的样例全部通过，1 表示契约断言失败。输出中的 `reply envelope` 检查版本、请求编号和布尔型成功标志。此次基线在 macOS、Apple clang 17、Node.js 22.14.0 和 ArduinoJson 7.4.3 上验证。

两端使用同一组请求和断言。固件端每个场景启动独立进程，通过真实 `handleFrame`、`submit`、控制任务的 `tick` 以及 `eventFrame` 处理请求和事件。单线程内存队列同步派发任务通知；采用合成的稳定航向和静止编码器反馈、已验证的距离尺度、受控设备时钟和已有内存 UART。两个连接各持有独立 Session，并访问同一控制器。固件启动次数取自动作分配计数。Android 端通过现有 `Controller.receive` 收发消息；其动作启动证据来自运行事件中出现的不同动作编号，两个会话分别收包，共享底盘上的动作历史与租约。测试用 `advance(ms)` 推进窗口及截止时间。

## 首次对照结果

生产代码版本 `938efbf`，从干净检出加入本目录后运行。Android 列记录对齐前的替身偏差，作为历史基线。对齐后的当前结果可用上述命令复跑。

| 场景 | 真实固件宿主机路径 | 固件 | Android 替身 |
| --- | --- | --- | --- |
| C1 握手 | 会话创建、能力与速度字段序列化、首次状态查询 | 通过 | 缺应答版本、启动标识和多项速度字段 |
| C2 错误会话 | 会话号检查，随后以正确会话查询 | 通过 | 错误码为 `BAD_SESSION`，协议要求 `SESSION` |
| C3 动作受理与重试 | 动作分配、请求键去重、应答与状态关联 | 通过 | 应答缺动作编号，重复请求产生新的运行事件编号 |
| C4 历史查询 | 停车结束 A、重新申请并启动 B、历史查找及快照合成 | 通过 | 按键和编号均返回当前快照，未知键仍成功 |
| C5 窗口与截止时间 | 新窗口续期、拒绝被取代窗口、持有者检查、失败后保留原期限 | 两次独立运行均通过 | 两次握手得到同一会话号，旧窗口被接受，未在原期限释放 |

C5 的一次运行在原截止前 1 ms 及截止时各读取一次快照，另一次验证使用当前窗口恢复续期。五组样例均已覆盖固件的生产判断。本套基线检验消息契约；真实 RTOS 调度、传输分片、串口时延及停车物理性能需另行验证。测试不会连接小车或向硬件输出 PWM。
